## 0. ROLE AND MISSION

You are a principal-level Laravel architect and full-stack engineer. Build **"Social Commerce Order Manager: Facebook/WhatsApp orders"**, a complete, production-grade, end-to-end business application. It must be the best application in its category worldwide: fast, secure, beautiful, multilingual, and complete enough that a business can run its whole operation on it.

The core idea: businesses that sell through Facebook Pages, Messenger, Instagram DMs, and WhatsApp receive orders as chat messages and comments. The app captures those conversations, turns them into structured orders (manually, by agent, or by AI), then manages everything after: customer, inventory, payment, courier, delivery, returns, accounting, staff, reports, and growth.

It must be **fully modular**: every module can be switched ON or OFF per business (and per branch). A business turns on only what it needs; the app must run correctly with any combination of modules enabled or disabled.

## 2. ARCHITECTURE RULES

1. **Multi-tenant**: one installation hosts many Businesses (tenants). Each business has Branches. Every tenant-owned table carries `business_id` (and `branch_id` where relevant) with global scopes enforced at the model layer plus policy checks. A test suite must prove no cross-tenant data leakage.
2. **Module system**: build a `Modules` registry. Each module is a self-contained folder (`app/Modules/<Name>` or `modules/<Name>`) with its own migrations, models, Filament resources/pages/widgets, policies, routes, translations, settings, seeders, and a `module.json` manifest (name, version, dependencies, permissions, menu entries, settings schema, events it emits/listens to).
3. **Module toggles**: table `business_modules` (business_id, branch_id nullable, module_key, enabled, settings JSON). Disabled module means: menu hidden, routes 404, policies deny, scheduled jobs skip, API endpoints return 403, widgets removed. Enabling a module with unmet dependencies must prompt to enable them; disabling one that others depend on must warn. Provide a Super Admin and Business Owner UI "Module Center" with plain-language descriptions, toggles, and an onboarding wizard that suggests module sets by business type (see 3.0 presets).
4. **Loose coupling**: modules communicate via domain events and interfaces, never by hard references to other modules' tables. Example: Orders emits `OrderConfirmed`; Inventory, Accounting, Courier, Notifications each listen only if enabled.
5. **Branches**: multi-branch with branch-level stock, staff, cash, reports, and permissions. A business with one branch must never see branch complexity unless it enables Multi-Branch.
6. **Everything auditable**: activity log on all important models (who, what, old/new, IP, device).
7. **API first**: every feature has a documented REST API (Sanctum tokens) plus webhooks out, so mobile apps can be built later. Generate OpenAPI docs.
8. **Queues for all slow work**: webhooks respond in under 200 ms and enqueue; AI calls, messaging, courier calls, PDF generation, imports, and scraping run on queues with retries, backoff, idempotency keys, and dead-letter handling.
9. **Settings**: central typed settings system (global, business, branch, user levels) with caching.
10. **Security by default**: see section 8.

## 8. SECURITY, QUALITY, PERFORMANCE (NON-NEGOTIABLE)

**Security**: strict tenant isolation tests; policies on every resource; mass-assignment protection; validation via Form Requests; webhook signature verification and replay protection; encrypted storage of tokens/secrets (Laravel encrypted casts), secrets never logged; CSRF, XSS, SQLi protection; secure file uploads (type/size/virus-scan hook, private storage with signed URLs); rate limiting on login, API, public forms, webhooks; 2FA; audit log; PII minimization and masking in logs and AI prompts (configurable); data export/delete requests; backup encryption; security headers (CSP, HSTS, etc.); dependency audit in CI.

**Performance**: eager loading everywhere (no N+1, enforce with `Model::preventLazyLoading()` in non-production), DB indexes on all filter/sort/foreign keys, composite indexes for tenant queries, cache heavy aggregates (with invalidation), paginated and virtualized large tables, queue everything slow, `drutogoti` on public pages and heavy lists, response caching for public pages, image optimization (WebP, lazy load), CDN-ready assets. Targets: public pages LCP under 2 s on mid-range mobile; common admin list pages under 300 ms server time at 100k orders; webhook ack under 200 ms.

**Reliability**: idempotent jobs, retry/backoff, circuit breakers for external APIs, failure alerts, health checks, graceful degradation when AI/courier/channel is down (queue and retry, show status to agents).

**Quality**: Pest tests for domain logic (order totals, taxes, stock reservation, module toggling, tenant isolation, webhook handling, AI extraction parsing with fixtures, courier status mapping, payment reconciliation, accounting postings balance), feature tests for each panel's main flows, browser smoke tests (Pest Browser/Dusk) for demo login and chat→order. Minimum 80% coverage on domain/services. Pint + Larastan in CI (GitHub Actions workflow included). Seeders and factories for every model. Strict types, DTOs/Actions pattern for business logic, thin controllers/resources, no logic in Blade.

**UX**: Filament panels themed per business (logo, colors), dark mode, fully responsive, global search, command palette, keyboard shortcuts, helpful empty states, inline help, guided tours for first use, accessible (WCAG AA basics), consistent Bangla/English typography (Noto Sans Bengali or similar, correct in PDFs too).
